# tabular-ml-pipeline: прогноз оттока клиентов

Учебный проект: бинарная классификация оттока (`Churn`) на датасете IBM Telco Customer Churn.

## Данные

- Источник: [IBM/telco-customer-churn-on-icp4d](https://github.com/IBM/telco-customer-churn-on-icp4d),
  файл `data/Telco-Customer-Churn.csv`, коммит `d5371f5d83a446ad5673cbcca3b814b926491f8a`.
- Лицензия репозитория: Apache-2.0. Это официальный пример IBM, источник доступен (проверено 2026-01-12).
- SHA-256 файла: `16320c9c1ec72448db59aa0a26a0b95401046bef5d02fd3aeb906448e3055e91`.
- 7043 клиента, 21 столбец, доля оттока 26.5%.

Данные в Git не хранятся, их скачивает скрипт.

## Установка и запуск

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m churn.download_data   # скачивание и проверка SHA-256
python -m churn.check_data      # проверка схемы, распределение цели -> results/data_summary.json
python -m churn.compare_models --ablation   # все модели на validation -> results/val_comparison.json
python -m churn.run_cv          # 5-fold CV и подбор параметров -> results/cv_search.json, cv_candidates.csv (~3.5 мин на 4 CPU)
python -m churn.final_eval      # порог по OOF и однократная оценка на test -> results/final_evaluation.json
python -m churn.analysis        # важность признаков, анализ ошибок, проверка утечки -> results/analysis_summary.json
pytest -q
```

EDA: `notebooks/01_eda.ipynb` (выполненный, с выводами). Графики сохраняются в `reports/figures/`,
краткая сводка в `results/eda_summary.json`. Перезапуск без Jupyter-интерфейса:

python -c "import nbformat; from nbclient import NotebookClient; nb=nbformat.read('notebooks/01_eda.ipynb', 4); NotebookClient(nb, resources={'metadata': {'path': 'notebooks'}}).execute(); nbformat.write(nb, 'notebooks/01_eda.ipynb')"

## Решения этапа 1

- Файл скачивается по фиксированному коммиту, а не по ветке `master`, и сверяется по SHA-256:
  если источник изменится, скрипт остановится, а не тихо обучится на других данных.
- Схема проверяется явно: состав и типы столбцов, уникальность `customerID`, значения цели.
  `TotalCharges` в сыром файле строковый; разбор этого столбца отложен до EDA.

## Решения этапа 2 (EDA)

- NaN в сыром файле нет. `TotalCharges` строковый из-за 11 пустых значений, и все они у клиентов
  с `tenure == 0` (новые клиенты). Им ставится `TotalCharges = 0` построчным правилом в
  `churn.data.clean_data`; правило не использует статистик выборки, поэтому утечки нет.
- `TotalCharges` почти равен `tenure × MonthlyCharges` (корреляция с `tenure` 0.83). Признак
  оставлен, мультиколлинеарность для линейной модели гасится регуляризацией.
- `customerID` уникален и исключён из признаков (`churn.data.FEATURES`), он нужен только для
  отслеживания разбиений.
- Сильнее всего с оттоком связаны стаж, тип контракта, интернет-услуги (`OnlineSecurity`,
  `TechSupport`), способ оплаты; `gender` и `PhoneService` почти не влияют.
- Отток 26.5%: дисбаланс умеренный, поэтому дальше смотрим PR-AUC и подбираем порог.

## Решения этапа 3 (разбиения и базовые модели)

- Разбиение 60/20/20 (train/validation/test), стратифицировано по `Churn`, seed 42. Сохраняется
  списком `customerID` в `results/splits.csv`, и все скрипты берут его из файла: test один и тот же.
- Предобработка собрана в `Pipeline` + `ColumnTransformer` (`churn/features.py`): медианная
  импутация и `StandardScaler` для чисел, `most_frequent` + `OneHotEncoder(handle_unknown="ignore")`
  для категорий. Так статистики считаются только на train, а неизвестная категория на инференсе
  не ломает модель. Тесты проверяют, что медианы и средние совпадают со статистиками train.
- `DummyClassifier(strategy="prior")` задаёт нижнюю границу качества.

Результаты на validation (порог 0.5, test не использовался):

| Модель | ROC-AUC | PR-AUC | F1 |
|---|---|---|---|
| Dummy | 0.5000 | 0.2654 | 0.0000 |
| LogisticRegression | 0.8361 | 0.6423 | 0.5900 |

## Решения этапа 4 (RandomForest и CatBoost)

- Каждая модель получает свою предобработку (`churn/models.py`):
  - LogisticRegression: one-hot + масштабирование;
  - RandomForest: медианная импутация и `OrdinalEncoder` без масштабирования (деревьям оно не нужно,
    а one-hot дробит категорию на много слабых бинарных признаков);
  - CatBoost: категории передаются строками через `cat_features`, кодирование делает сам CatBoost
    (ordered target statistics); пропуск категории становится отдельным значением.
- `--ablation` добавляет деревья с one-hot предобработкой, чтобы проверить это решение данными.

Результаты на validation (порог 0.5, фиксированные параметры, test не использовался):

| Модель | ROC-AUC | PR-AUC | F1 |
|---|---|---|---|
| Dummy | 0.5000 | 0.2654 | 0.0000 |
| LogisticRegression | 0.8361 | 0.6423 | 0.5900 |
| RandomForest (ordinal) | 0.8347 | 0.6384 | 0.5335 |
| CatBoost (native cat) | 0.8329 | 0.6401 | 0.5590 |
| RandomForest (one-hot) | 0.8349 | 0.6300 | 0.5500 |
| CatBoost (one-hot) | 0.8273 | 0.6322 | 0.5364 |

Нативная обработка категорий в CatBoost немного лучше one-hot по обеим AUC; для леса
разница в пределах шума. Все модели близки к логистической регрессии: на validation из
1409 клиентов разница в сотые доли AUC не значима, поэтому сравнение переносится на
кросс-валидацию (этап 5). F1 при пороге 0.5 занижен из-за дисбаланса, порог подбирается
на этапе 6.

## Решения этапа 5 (кросс-валидация и подбор параметров)

- Одна validation-выборка из 1409 клиентов шумная, поэтому модели сравниваются 5-fold
  `StratifiedKFold` на development-наборе (train + validation = 5634 клиента). Test не используется.
- В `GridSearchCV` передаётся весь `Pipeline`, поэтому импутация, кодирование и масштабирование
  обучаются заново внутри каждого fold. Тест сверяет статистики scaler в каждом fold
  с обучающей частью именно этого fold.
- Сетки ограничены (8–18 комбинаций на модель, `churn/tuning.py`). Метрика выбора: средний
  PR-AUC, потому что положительный класс редкий и важна точность среди отобранных клиентов.
- CatBoost пришлось обернуть в небольшой sklearn-совместимый класс `CatBoostCatClassifier`:
  `CatBoostClassifier` копирует `cat_features`, и `sklearn.clone` отказывается его клонировать.

Результаты 5-fold CV (среднее ± стандартное отклонение по fold):

| Модель | Лучшие параметры | PR-AUC | ROC-AUC |
|---|---|---|---|
| Dummy | – | 0.2654 ± 0.0001 | 0.5000 ± 0.0000 |
| LogisticRegression | C=1.0, class_weight=None | 0.6612 ± 0.0176 | 0.8459 ± 0.0083 |
| RandomForest | max_depth=8, min_samples_leaf=5, max_features=sqrt, 300 деревьев | 0.6670 ± 0.0214 | 0.8470 ± 0.0095 |
| CatBoost | depth=4, learning_rate=0.03, l2_leaf_reg=10, 500 итераций | 0.6738 ± 0.0236 | 0.8502 ± 0.0089 |

CatBoost лучший по среднему, но отрыв (0.007–0.013 PR-AUC) меньше разброса между fold. На тех же
fold он лучше логистической регрессии во всех пяти и лучше леса в четырёх из пяти, так что
преимущество устойчивое, хотя и небольшое. Лучшие параметры CatBoost лежат на краю сетки
(меньшая глубина, меньший шаг, сильнее регуляризация), то есть сетку можно расширить в эту сторону.

## Решения этапа 6 (порог и финальная оценка)

- Модель и параметры берутся из `results/cv_search.json` (CatBoost). Порог выбирается по
  out-of-fold предсказаниям на development-наборе, критерий: максимум F1 на сетке 0.05–0.95.
  Для OOF используется новое разбиение на fold (seed 43), чтобы порог не подгонялся под те же
  fold, на которых выбирались параметры.
- Затем модель обучается на всём development-наборе и оценивается на test один раз с уже
  зафиксированным порогом. Другие модели на test не оценивались: test нужен для
  несмещённой оценки выбранной модели, а не для ещё одного выбора.
- OOF и test предсказания сохранены в `results/oof_predictions.csv` и `results/test_predictions.csv`,
  кривые в `reports/figures/final_curves.png`.

Порог 0.35 (OOF F1 0.640 против 0.605 при пороге 0.5). Метрики на test (1409 клиентов, 374 ушедших):

| ROC-AUC | PR-AUC | F1 | Precision | Recall |
|---|---|---|---|---|
| 0.8447 | 0.6661 | 0.6300 | 0.5604 | 0.7193 |

Матрица ошибок на test: TN 824, FP 211, FN 105, TP 269. Метрики test близки к CV
(ROC-AUC 0.850 ± 0.009, PR-AUC 0.674 ± 0.024), то есть переобучения на выборе параметров не видно.

## Решения этапа 7 (важность признаков и анализ ошибок)

Все расчёты на development-наборе; test после однократной оценки больше не используется.

- **Permutation importance** считается внутри 5-fold CV: модель обучается на обучающей части fold,
  признаки перемешиваются на отложенной, падение PR-AUC усредняется. Это честнее, чем на train,
  где модель видела данные. Топ: `tenure` (0.096), `Contract` (0.060), `InternetService`,
  `MonthlyCharges`, `TotalCharges`. `gender`, `PhoneService` почти ничего не дают.
- **Важность CatBoost** (`PredictionValuesChange`, средний |SHAP|) ставит на первое место `Contract`,
  затем `MonthlyCharges` и `tenure`. Расхождение с permutation importance ожидаемо: `tenure`,
  `TotalCharges` и `Contract` коррелированы, и встроенная важность делит вклад между ними иначе.
  Таблица: `results/feature_importance.csv`, график: `reports/figures/feature_importance.png`.
- **Ошибки** (OOF, порог 0.35, `results/error_analysis.csv`, `reports/figures/error_rates_by_group.png`):
  - FP сосредоточены у клиентов с помесячным контрактом (98% всех FP), стажем до полугода (FP rate
    53%), оплатой электронным чеком и оптоволокном. Это группы с высоким базовым оттоком: модель
    по сути предсказывает «типичный профиль ушедшего» и не различает, кто из них останется.
  - FN почти полностью у долгосрочных контрактов: модель не находит ни одного ушедшего клиента
    с двухлетним контрактом и 95% ушедших с годовым; также пропускает клиентов без интернета и со
    стажем больше 4 лет. Признаков, отличающих этих редких ушедших, в данных нет.
- **Проверка утечки**:
  - `customerID` не входит в признаки.
  - Одномерный ROC-AUC каждого признака (неглубокое дерево в CV) не выше 0.74 (`Contract`);
    признаков, почти совпадающих с целью (порог 0.9), нет.
  - 48 строк имеют полностью совпадающие признаки, в 11 таких группах метки различаются: шум
    небольшой.
  - Риски, которые нельзя проверить без временных меток: датасет является срезом, и состав услуг
    или тип контракта могли измениться в процессе ухода (клиент отключает услуги перед уходом);
    `tenure` и `TotalCharges` у ушедших считаются до даты ухода, у оставшихся до даты среза.
    В продакшене все признаки должны браться на дату прогноза. В расширенной версии датасета IBM
    есть явные утечки (`Churn Score`, `Churn Reason`, `CLTV`), в используемой версии их нет.
